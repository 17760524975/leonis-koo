# v0.61 包体体检与瘦身方案（分析，未改代码）

> 起因：用户反馈「包体过大，留给扩展关卡的空间不够」。
> 结论先说：**真正的瓶颈不是关卡数据**（93 关只占 179.5 KB / 5.5%），
> 而是 **4 首背景音乐 2.01 MB（63%）** + **未压缩的 JS 773 KB（24%）**。
> 只把 BGM 挪出主包，主包就从 3.18 MB 掉到 1.18 MB，余量从 0.82 MB 变成 2.82 MB（≈1500 关）。

工具：`node tools/audit_package.js`（可随时复跑，输出同样三张表）。

---

## 一、包体规则（官方）

| 项目 | 限制 |
|---|---|
| 主包 | **≤ 4 MB** |
| 主包 + 全部分包 | ≤ 30 MB |
| 单个普通分包 | 不限大小 |
| 单个独立分包 | ≤ 4 MB |

出处：`微信小游戏 · 代码包` / `分包加载` 官方文档（"整个小游戏所有主包+分包大小不超过 30M，主包不超过 4M"）。

所以「扩展关卡」的硬约束是 **主包 4 MB**，不是 30 MB —— 但主包可以只装引擎与首屏，资源进分包。

补充事实（都影响方案选择）：

- BGM **已经是低码率**了：48 kbps 单声道、32 kHz、每首 90 秒。再往下压（32 kbps）每首只能省 ~170 KB，且听感明显变差 —— 所以音频不宜「再压」，宜「移出主包」。
- 视频/音频白名单里**没有 webp**（`png jpg jpeg gif svg ... mp3 wav ...`），所以图片只能走 PNG / JPEG，不能靠 WebP 省体积。
- `cloudfunctions/`（85 KB）是 `cloudfunctionRoot`，不进小游戏代码包，本次统计已排除；`.cloudbase/`、`project.private.config.json` 也已在 `packOptions.ignore` 里。
- 这里的数字是**磁盘体积**。真实包体以上传预览为准：`*.js` 会被 ES6→ES5 编译（可能变大），`uploadWithSourceMap: true` 另算。

## 三、关卡数据不是瓶颈

```
93 关 / 179.5 KB → 每关 1.93 KB
```

也就是：**再扩 100 关只要 190 KB**。当前 0.82 MB 余量理论上还能放 **433 关**。
所以「扩展关卡空间不够」的真实原因，是 BGM + 图片 + 未压缩代码把主包吃到了 79.6%。

顺带：`levels.js` 是 6 空格缩进的漂亮 JSON，**去掉缩进/换行后只剩 73.0 KB**，
光这一项白送 106.6 KB（相当于 55 关的数据量）。

## 四、方案（按性价比排序）

### P0 · BGM 移出主包（分包）—— 主包 3.18 → 1.18 MB

```
game.json:
  "subpackages": [{ "name": "audio", "root": "audio-pkg/" }]

audio-pkg/
  game.js                 ← 空入口（module.exports = {}），目录型分包需要它
  assets/audio/bgm_*.mp3  ← 4 首整体搬过来
```

`js/config.js` 的 `AUDIO.base` 改成 `'audio-pkg/assets/audio/'`，
`game.js` 启动时静默预下载，第一次解锁音频前等就绪：

```js
var bgmPkg = 0;                     // 0 未开始 / 1 加载中 / 2 成功 / 3 失败
function ensureBgmPkg(cb) {
  if (bgmPkg === 2) return cb(true);
  if (bgmPkg === 3) return cb(false);
  if (!wx.loadSubpackage) { bgmPkg = 3; return cb(false); }
  if (bgmPkg === 1) { BGM_WAIT.push(cb); return; }
  bgmPkg = 1; BGM_WAIT.push(cb);
  wx.loadSubpackage({
    name: 'audio',
    success: function () { bgmPkg = 2; flush(true); },
    fail: function () { bgmPkg = 3; flush(false); }   // 失败就静音，不影响玩法
  });
}
```

- 收益：**−2.01 MB**，主包余量 0.82 → 2.82 MB（≈1500 关）。
- 附带收益：首屏少下 2 MB，冷启动更快；BGM 只在进对局时才需要。
- 风险：分包加载失败会没音乐（已有主页合成轻音乐兜底）；`audio-pkg` 下的 mp3 路径要整体改前缀，容易漏改 `bgmPath()`。
- 为什么不用「云存储 / CDN 流式」：更省主包，但要配 `downloadFile` 合法域名 + 首次播放有网络延迟，且断网无音乐。小游戏离线包体优先用分包。

### P1 · 代码瘦身 —— 773 KB → 约 420 KB

| 手段 | 省 |
|---|---|
| `levels.js` 紧凑化（去缩进换行，73 KB） | −106.6 KB |
| `core.js` / `config.js` / `game.js` 去注释 + 去行首缩进 | −200 KB 量级 |
| 其余小文件（geom / judge / cloud…） | −15 KB 量级 |

两种做法：

1. **打包期压缩**（推荐）：新增 `tools/pack.js`，`sync` 时产出「去注释 + 紧缩」版本到 `miniprogram/js/`，`js/` 保持可读源码。
   代价：`verify_v059/v060` 里「三端 md5 一致」的断言要改成「去注释后语义一致」。
2. 交给开发者工具：`project.config.json` 的 `setting.minified` 在 game 项目上是否生效随版本而异，建议直接看「上传预览」里的数字验证；不稳。

⚠️ 不要用 uglify 那类「改标识符」的压缩做**全量**替换：本工程大量依赖 `indexOf`/`brace` 定位的构建脚本（`build_zodiac_levels.js` 等）会失配。

### P2 · 图片 —— 335 KB → 约 170 KB

| 文件 | 现状 | 目标 |
|---|---|---|
| `home_bg_desk.png` 750×1624 | 185.9 KB | JPEG q85 ≈ 95 KB |
| `board_paper.png` 800×800 | 148.9 KB | JPEG q82 ≈ 60 KB |

注意：JPEG 无 alpha，这两张若有透明通道就不能直接换（WebP 白名单不支持）。
本机没有 ffmpeg / ImageMagick / Pillow，需要先 `pip install pillow` 或装 ImageMagick 才能转。

### P3 · 从源头减音频（可选）

4 首 × 90s。若愿意牺牲「每 5 关换一首」的丰富度：

- 保留 2 首（主歌 + 变奏）：−1.0 MB；
- 或每首裁到 45s 无缝循环：−1.0 MB。

属于体验取舍，建议先做 P0，做完后主包已经够用，这一条可以不动。

另外提醒两件与包体无关、但会拖慢上传 / 协作的事：

- 研发工程目录 **117 MB**（`tools/out` 的截图、`art-src` 5.4 MB、`_upgrade_backup*`、`audio-src`），不影响小游戏包体，但会让 `git clone` 与上传都变慢，建议给 `tools/out` 加 `.gitignore`。
- `uploadWithSourceMap: true` 会上传 sourcemap，不占包体但增加上传耗时；线上包可以关掉。
