# v0.62 BGM 分包 + 代码瘦身 + 运行性能优化

> 用户要求：P0（BGM 分包）与 P1（代码瘦身）一起做，并按
> [微信小游戏《运行性能》](https://developers.weixin.qq.com/minigame/dev/guide/performance/perf-action-runtime-overview.html)
> 优化游戏性能。
>
> 结果：**主包 3.18 MB → 0.83 MB（上限 4 MB 的 20.9%）**，同样余量能再放
> **≈3300 关**（原 433 关）；稳定帧的**全屏填充减半、渐变与测宽调用归零**，
> 低端机阴影全关、粒子 45%、30fps，静态浮层不再每帧重画。

## 一、包体：主包 3.18 MB → 0.83 MB

`node tools/audit_package.js` 现在会读 `game.json` 的 `subpackages`，把主包与分包分开算：

| | 修前 | 修后 |
|---|---|---|
| 主包 | 3.18 MB（79.6%） | **0.83 MB（20.9%）** |
| 分包 `audio-pkg/` | — | 2.01 MB（4 首 BGM） |
| 全包合计 | 3.18 MB | 2.84 MB（上限 30 MB 的 9.5%） |
| 关卡数据 | 179.5 KB（1.93 KB/关） | **90.5 KB（0.97 KB/关）** |
| 主包余量 ≈ 可再放 | 433 关 | **3330 关** |

### P0 · BGM 进分包

```
miniprogram/
  audio-pkg/
    game.js                    ← 分包入口（小游戏硬性要求，空壳即可）
    assets/audio/bgm_lv1~4.mp3 ← 4 首，共 2.01 MB
  assets/audio/                ← 主包只剩 5 个短音效（85 KB）
```

`game.json`：

```json
"subpackages": [{ "name": "audio", "root": "audio-pkg/" }]
```

**小游戏与小程序的差异（踩过的坑）**：分包 root 目录下**必须**有 `game.js`，
否则开发者工具/真机编译直接报「未找到 ["subpackages"][0]["root"] 对应的
/audio-pkg/game.js 文件」。纯资源分包也要放一个空壳入口。

加载策略（`miniprogram/game.js`）：

- **首次触摸**就 `wx.loadSubpackage({name:'audio'})` 静默预取 —— 玩家在主网点两下再进关，
  2 MB 通常已经下完；不占首屏冷启动。
- **未就绪绝不建 `InnerAudioContext`**：src 指向分包路径，提前建必然加载失败，
  而且错误会被实例记住。`ctxFor()` 里有一道 `bgmPkgReady()` 闸门。
- 就绪后回调补播：进关时若还在下载，先让主页合成曲继续响，下载完自动切关卡曲，
  中间不会出现「安静一下」。
- **失败 = 静音降级**（主页仍有零文件的合成轻音乐），60 秒后允许重试一次，
  网络恢复的用户不用重启小程序。

### P1 · 代码瘦身（`tools/lib/pack.js`）

`sync` 时把 `js/*.js` 打成「去注释 + 去缩进」产物写进 `preview/js` 与 `miniprogram/js`，
`js/` 始终是可读源码。**刻意不做**改标识符/合并行：本工程的构建脚本靠
`indexOf`/花括号配对定位源码，改名会失配；合并行会踩 ASI。

| 模块 | 前 | 后 | 省 |
|---|---|---|---|
| core.js | 436.1 KB | 233.3 KB | 47% |
| levels.js | 179.5 KB | 90.5 KB | 50% |
| config.js | 72.9 KB | 17.4 KB | 76% |
| judge.js | 8.1 KB | 4.3 KB | 47% |
| geom.js | 11.3 KB | 7.2 KB | 36% |
| **合计** | **708.0 KB** | **352.8 KB** | **50%** |

正确性靠三层保证：

1. `node tools/sync.js --check`：产物必须逐字等于 `strip(源码)`（strip 迭代到不动点，幂等）；
2. 产物本身 `node --check` 通过；
3. **`verify_v062` 直接用 `miniprogram/js` 的产物跑 93 关标准解，93/93 通关**。

三端一致性断言随之从「逐字节 md5」改成「语义 md5」：`md5()` 对 `.js` 先 normalize，
对 `mp3/wav` 仍按原字节（25 个历史脚本各改一行，定义里加 `/\.js$/` 判断）。

## 二、运行性能：逐条对照官方《运行性能》

| 官方建议 | 我们的做法 | 可验证的结果 |
|---|---|---|
| **机型适配**（`getSystemInfoSync` 的 benchmarkLevel） | `deviceTier()` 读 `wx.getDeviceInfo().benchmarkLevel`：<10 低端 / <20 中端 / 其余高端（iOS 取不到按高端） | 档位进 `state.quality`，低端 30fps |
| **控制计算频率**（`wx.setPreferredFramesPerSecond`） | 低端档启动时设 30fps；静态浮层另外做**跳帧** | 排行榜静置 160ms：**0 次重画**（旧版 10 次） |
| **减少临时对象 / 对象池** | 渐变对象缓存、测宽缓存、粒子数组复用 | 稳定帧 `createLinearGradient` **14 → 0**、`measureText` **13 → 0** |
| **降低填充率**（渲染开销） | dpr 上限按档位 2.5 / 2 / 1.75；删掉每帧第二次全屏填充 | 每帧全屏填充 **2 次 → 1 次**；dpr 3→2 填充量 −56% |
| **关注 GC** | `wx.triggerGC()` 每局开始/结束各一次 | `gcHint()` 挂在 `setupLevel` 与结算两条退出路径 |
| **资源尽快释放**（`onMemoryWarning`） | 告警时 `trimMemory()`：清渐变/测宽缓存、丢粒子层，再 `triggerGC` | 贴图与存档**不动**，可玩性不受影响 |
| **纹理压缩 / 图集合批** | 本作只有 2 张图、且是整屏背景，合并无意义 | 留给 P2（转 JPEG 可再省 160 KB） |

### 具体改动

1. **画质分级 `state.quality`**（core）：`shadow` / `particles` / `fps` 三个系数。
   低端 `shadow=0`（Canvas2D 的 `shadowBlur` 是 CPU 高斯模糊，最贵的特效）、
   粒子 45%；中端 55% / 70%；高端全开。26 处 `ctx.shadowBlur = X` 统一走 `qShadow(X)`。
2. **dpr 上限**（game）：3 → 2.5 / 2 / 1.75。七巧板是纯色矢量，dpr 2 与 3 肉眼差别极小，
   但填充量差 2.25 倍。
3. **单次全屏填充**：旧版 `frame()` 按设备像素填一遍、`render()` 又按设计像素填一遍。
   现在只留 `frame()` 那次。
4. **渐变缓存**：背景三段渐变、左上柔光、主按钮 / 糖果按钮、板件五种纹理、图标徽章全部缓存。
   板件按「样式 + 量化 bbox（1px）」做 key：静置 100% 命中，拖动时只有正在动的那块每帧新增 2 个 key。
   换肤 / 转屏 / `trimMemory` 时整表清空。
5. **测宽缓存**：key = 当前 `ctx.font` + 文字，上限 400 条。HUD、胶囊、昵称截断全部命中。
6. **粒子分级**：`buildFxParts` 与通关彩带按档位缩放（`qParticles`）。
7. **静态浮层跳帧**：`rank / skin / buy / energy / online / invite` 六个浮层无动画无倒计时，
   静置时不重画（Canvas 内容会保留）；**1 秒心跳**兜住异步到达的头像 / 榜单 / 余额；
   任何输入、`persist()`、`applyProfile()`、榜单回包、滑动都会立刻标脏重画。
   `settings` 特意不列入：头像与授权状态是异步的，原生按钮浮在画布上，少画一帧会露馅。

## 三、验收

```bash
node tools/audit_package.js    # 主包/分包账（游戏包）
node tools/sync.js --check     # 产物 == strip(源码)
node tools/verify_v062.js      # 52 项：分包 / 瘦身 / 产物跑 93 关 / 渲染开销
node tools/shot_v062.js        # 5 张截图（主页 / 关卡 / 对局 / 结算 / 提示）
```

`verify_v062` 的关键断言（都在真实渲染路径上量，不是读源码猜）：

- 每帧全屏填充 **1** 次、稳定帧 `grads=0` / `meas=0`、一帧绘制调用 126；
- tier 0 一帧里 `shadowBlur` 最大值 **0**；粒子 22 → 10（45%）；
- 排行榜静置 160ms 内 **0** 重画，1s 心跳重画 1 次，`dirty` 立刻重画；
- `trimMemory()` 后下一帧渐变重建（缓存确实清空）；
- 打包产物跑 93 关标准解 **93/93**。

全量回归：**50 个 `verify_*.js` 全部 exit 0**。历史脚本只改了两类断言
（三端 md5 → 语义 md5、音频路径指向分包），玩法断言一条没松。

## 四、风险与后续

- **真机包体请以「上传预览」为准**：`*.js` 会做 ES6→ES5 编译（可能变大），
  `uploadWithSourceMap: true` 会另传一份 map（不占包体但增加上传耗时）。
- 分包首次下载 2 MB 视网络约 0.5~3 秒；期间进关是**没有关卡曲**的（主页曲继续响），
  不影响操作与判定。
- `trimMemory` 不丢 `images`（丢了两张背景图会闪白），内存告急时主要收益来自
  渐变/测宽表与粒子数组，量级几十 KB~百 KB，属于"温和释放"。
- 可选的 P2 还没做：两张 PNG 转 JPEG 约再省 160 KB（本机没有 Pillow/ImageMagick）。
  现在主包只用 20.9%，不着急。
