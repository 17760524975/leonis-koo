## 一、提示面板：两枚按钮尺寸统一

### 问题

两枚按钮是**两段独立的常量**，历史上各自调过，最后叠在一起差了一圈：

| 按钮 | 修前 | 修后 |
|---|---|---|
| 巧币（`30 · 买 1 次`） | 440 × 84，字号 26 | **480 × 92，字号 28** |
| 视频（`免费一次`） | 480 × 92，字号 28 | **480 × 92，字号 28** |
| 道具（`用查找道具 · 剩 N`，有道具时才出现） | 480 × 96，字号 28 | **480 × 92，字号 28** |

视觉后果不只是"差一点"：巧币按钮小一圈 + 描边样式（`secondary`）更浅，
玩家截图里它读起来像「次要链路」，而实际上花巧币是比看视频更划算的那条。
统一后三行同宽同高、同字号，差异只靠**颜色**表达（橙金 = 可买 / 红 = 看视频）。

### 改法

三处常量改成同一组数（`js/core.js` 的 `renderHint`），不再各写各的：

```js
var bCoin = { id: 'hint_coin', w: 480, h: 92, size: 28, icon: 'coin',  iconInline: true };
var bAd   = { id: 'hint_ad',   w: 480, h: 92, size: 28, icon: 'video', iconInline: true };
var bItem = { id: 'hint_item', w: 480, h: 92, size: 28 };
```

纵向间距仍是 104（92 按钮 + 12 间隙），面板高度 616 不用动，底部「本关还可看 3/3 次」
与 × 位置不变。

### 验收

`verify_v060.js` 第 3 组不是靠读源码就算通过 —— 它用假 canvas 记录**每条闭合路径的外框**，
再把渲染出来的 480×92 矩形去重比对：

```
[OK] 两枚按钮外框宽高完全相等    480.0×92.0 vs 480.0×92.0
[OK] 两枚按钮水平中心重合        375.0 vs 375.0
[OK] 两枚按钮纵向间距 104        104.0px
[OK] 两枚按钮的字号一致（28）
```

## 二、三星门槛：从 `parTime` 收到 `parTime × 0.8`

### 原规则为什么偏松

```
3★ = 用时 ≤ parTime      且 步数 ≤ parSteps
2★ = 用时 ≤ parTime × 1.6
```

`parTime` 是按「正常发挥」标的（七巧板 80~130 秒），而每关时限统一 150 秒。
也就是说**只要拼完，用时几乎必然 ≤ parTime**，三星的唯一真实门槛只剩步数；
玩家体感就是「拼完就给三星」，星级没有区分度，拿去做排行榜等于人人满分。

### 新规则

```
3★ = 用时 ≤ parTime × 0.8  且 步数 ≤ parSteps      ← 唯一改动
2★ = 用时 ≤ parTime × 1.6                          ← 不动
1★ = 其余
```

| 数据集 | 关卡数 | parTime 区间 | 三星窗口（修后） | 平均窗口 | 占时限 150s |
|---|---|---|---|---|---|
| 几何 + 生肖（tangram7） | 57 | 80 ~ 130s | 64 ~ 104s | 74.7s | 50% |
| 几何（tangram4） | 36 | 78 ~ 114s | 62.4 ~ 91.2s | 81.4s | 54% |

全 93 关的三星窗口都落在时限的 **50%~69%**，最短 62.4 秒（四巧板第 1 关），
不存在「短到不可能」的关。

### 为什么只动时间、不动步数

`parSteps` 已经是紧口径：**一次拖放 = 1 步，每转 45° = 1 步，翻转 = 1 步**，
七块板只给 18~29 步（每块 2~2.6 步）。再收紧，玩家就只能靠「不旋转硬凑角度」，
那不是难度而是别扭 —— 板子有 8 个角向，靠手算角度而不是靠看形状，体验会崩。

### 为什么二星不动

二星保持「按时拼完即可」。这样星级分布是 **2★ 为主、3★ 稀缺**：

- 手生玩家：拼完就有 2★，正反馈不断；
- 熟手：要靠更少的旋转、更直的拖放去压时间和步数；
- 排行榜：3★ 变成真·高手标记，而不是「通关次数」的同义词。

### 经济上不需要改

星级奖励是**总额制**（1★2 / 2★3 / 3★5 巧币，每关封顶 5）。三星变难只是让
「补差到 5」这条路变长，不会因为难度变化产生新的刷币口子；`starPaid` 的补差价
逻辑与本次改动无关，未动。

### 验收

`verify_v060.js` 第 2 组在**真实的 `win()` 流程**上打四档边界，抽 3 关（首关 / 蛇 / 末关）：

```
[OK] 用时 79% par + 步数刚好  → 3★
[OK] 用时 95% par + 步数刚好  → 2★     ← 旧口径这里还是三星
[OK] 用时 50% par 但步数超一档 → 2★
[OK] 用时 170% par            → 1★
```

## 三、排行榜这件事没有一起改（用户选择）

星级要上榜，本来需要一个「星数榜」：`players` 集合里早就有 `stars` 字段
（`collectCloud()` 按两个数据集累加，满分 171），但云函数 `rankOf()` 的 tab0
仍按 `cleared` 排序。本次按用户选择**只调难度**，榜单未动 —— 等要真上星数榜时，
需要同时改 `miniprogram/cloudfunctions/player/index.js` 的 `field` 并重新上传云函数，
否则前端显示 `N ★` 而后端按通关数排序，数字会对不上。
