| `sfx_win` 峰值 | -9.00 dBFS | @gain 1.00 → **+19.5 dB** |
| `sfx_pick` 峰值 | -11.00 dBFS | @gain 0.90 → **+17.1 dB** |
| `sfx_tap` 峰值 | -12.00 dBFS | @gain 0.80 → **+15.0 dB**（刻意最轻，但仍在安全线以上） |

**判据**：音效峰值必须高出 BGM 底噪 **≥10 dB**，否则会被埋掉。四个音效全部通过（最低 +15.0 dB）。

> **⚠️ 一处对原规格的调整（已由主理人 2026-11-18 拍板确认，定稿）**
>
> 任务里写"音效峰值约 -12 dBFS"。我按 -12 交付后实测发现：**-18 LUFS 的 BGM 配上 90 ms 的短促瞬态，snap 的能量比 BGM 底噪还低 1.5 dB——会被埋掉**。
> 原因是"峰值"和"可听度"对极短瞬态不是一回事：90 ms 的音效峰值 -12，但能量集中在头 20 ms，感知响度远低于同等峰值的持续音。
>
> **定稿取值**：`sfx_snap` -8 / `sfx_win` -9 / `sfx_pick` -11 / `sfx_tap` -12 dBFS，**BGM 严格 -18 LUFS 不动**。
>
> ❗ **程序不要做的事**：不要把这些文件再乘 0.63 去"还原成 -12"，也不要为了"配合 -12"把 BGM gain 降到 0.18。原规格的 -12 dBFS 已被推翻，按本文档 §4.3 的 gain 表执行即可。

## 4. 接入说明

### 4.1 前置：移动端音频解锁（硬性）

浏览器与微信小游戏都禁止自动播放。BGM 与全部音效**必须在用户第一次点击之后才响**。

- 解锁点：主界面 `开始` / `继续` 按钮的点击回调里
- 在解锁之前**不要**创建 BGM 播放，也不要 throw 异常——静音跑完主界面第一屏是正常的
- 微信小游戏的 `WebAudioContext` 在 iOS 上同样需要在用户手势里 `resume()`

### 4.2 推荐实现（Web Audio，低延迟 + 可随机化）

```js
// ---- 1. 解锁（放进"开始"按钮的点击回调） ----
const ac = (typeof wx !== 'undefined' && wx.createWebAudioContext)
  ? wx.createWebAudioContext()
  : new (window.AudioContext || window.webkitAudioContext)();
if (ac.state === 'suspended') await ac.resume();

// ---- 2. 预加载（主界面停留时跑，进对局前必须加载完 sfx_snap） ----
const buf = {};                       // name -> AudioBuffer
async function loadAudio(name, url) {
  const r = await fetch(url);
  buf[name] = await ac.decodeAudioData(await r.arrayBuffer());
}
await Promise.all([
  loadAudio('bgm_main', 'assets/audio/bgm_main.mp3'),
  loadAudio('sfx_snap', 'assets/audio/sfx_snap.wav'),
  loadAudio('sfx_win',  'assets/audio/sfx_win.mp3'),
  loadAudio('sfx_pick', 'assets/audio/sfx_pick.wav'),
  loadAudio('sfx_tap',  'assets/audio/sfx_tap.wav'),
]);

// ---- 3. BGM 循环（精确无缝，参数见 §6） ----
const bgmSrc  = ac.createBufferSource();
bgmSrc.buffer = buf.bgm_main;
bgmSrc.loop    = true;
bgmSrc.loopStart = 1105 / 44100;              // 0.025057 s
bgmSrc.loopEnd   = (1105 + 3087000) / 44100;  // 70.025057 s
const bgmGain = ac.createGain();
bgmGain.gain.value = cfg.settings.bgm ? 0.30 : 0;
bgmSrc.connect(bgmGain).connect(ac.destination);
bgmSrc.start();

// ---- 4. 音效（每次轻微变调，避免几十次一模一样） ----
const SFX_GAIN = { sfx_snap: 1.00, sfx_win: 1.00, sfx_pick: 0.90, sfx_tap: 0.80 };
let snapVoices = 0;                    // 并发限制
function playSfx(name) {
  if (!cfg.settings.sfx || !buf[name]) return;
  if (name === 'sfx_snap') { if (snapVoices >= 2) return; snapVoices++; }
  const s = ac.createBufferSource();
  s.buffer = buf[name];
  // ±5% 随机变调：90 ms 的木头声听不出音高差，但能彻底打散"复读机"感
  s.playbackRate.value = 1 + (Math.random() * 0.10 - 0.05);
  const g = ac.createGain();
  g.gain.value = SFX_GAIN[name] * (0.95 + Math.random() * 0.10);  // ±5% 随机音量
  s.connect(g).connect(ac.destination);
  s.onended = () => { if (name === 'sfx_snap') snapVoices--; };
  s.start();
}
```

### 4.3 触发事件对照表（精确到代码事件）

| 音效 | 触发点（不要提前也不要延后） |
|---|---|
| `sfx_pick` | `pointerdown` 命中板件、且判定为"开始拖拽"的那一刻（**不是** `pointerup`） |
| `sfx_snap` | 顶点吸附命中、赋值新坐标**同一帧**（§5.5 吸附反馈：板 1.06 倍回弹 + 描边高亮 + 8 ms 震动 同步） |
| `sfx_win` | 三条件判定通过、成局动效开始的同一帧（结算面板 400 ms 后出现，音效先响） |
| `sfx_tap` | 任意按钮 `pointerdown`（按下即响，符合"按下下沉 2px"的手感） |

**并发限制**：
- `sfx_snap` 同时最多 **2 个**（正常不会超过，但连点旋转后快速吸附可能叠）
- `sfx_tap` 同时最多 **2 个**，两次之间如果小于 40 ms，直接丢弃后一次（避免连点变成机关枪）
- 其它无限制

### 4.4 BGM 生命周期

| 场景 | 处理 |
|---|---|
| P1 主界面（解锁后） | 开始播放，`loop` |
| P1 → P2 关卡选择 | **不换曲**，继续播（同一首，保持连续性） |
| P2 → P3 对局 | **不换曲、不重头**（同一首 BGM 贯穿，"一局接一局"不要让玩家听到 restart） |
| P3 通关 → P4 结算 | **不换曲**，BGM 压低到 0.18（−4 dB），让 `sfx_win` 露出来；面板关闭后回 0.30 |
| 回到 P2 / P1 | 回 0.30 |
| 切后台（`wx.onHide`） | `bgmGain.gain.value = 0` 或 `suspend()`（计时暂停，音频也要停） |
| 回前台（`wx.onShow`） | 恢复。**不需要重新 resume**（已解锁过）；若 `ac.state === 'suspended'` 再 resume 一次 |
| 设置里关掉音乐 | 0.30 → 0（**不要 stop**，保持播放位置，否则重开音乐从头开始会突兀） |
| 设置里关掉音效 | `playSfx` 直接 return |

> v0.1 无广告、无插屏，所以没有"广告期间暂停 BGM"的问题。v0.2 接入广告时记得 `onHide`/`onShow` 那一套。

> ❗ **最容易漏的一条（主理人特别点名）**：结算面板关闭后**必须把 BGM 从 0.18 恢复到 0.30**。
> 结算面板有三个出口（`下一关` / `重玩` / `回列表`），三处都要恢复。建议不要在这三个按钮里各写一遍，而是把"面板可见性"做成单一状态，用 `watch`／统一渲染函数根据它推导 gain——否则一定会漏掉一条路径，玩家会以为"游戏音突然变小了"。

## 5. 声音设计细节（策划验收时看这里）

### 5.1 `sfx_snap` —— 为什么玩家听几十次不会腻

这是全游戏最重要的音效：一局听 4 次以上，多局听几十次。做得不对会变成"复读机"。四条设计约束：

**① 完全不承载音高。**
声音的能量由**噪声**承担，而不是由谐振承担。噪声的周期自相关接近 0，大脑无法从中提取音高，也就不会累积"又是这个音"的旋律记忆。
实测：音高显著度 **0.147**（纯噪声水平约 0.1–0.3，能听出音的地方 >0.55）。

> 我第一版就是用"一组非谐波比例的短谐振"做的，听起来"木头"没错，但实测 619 Hz 的谱峰比邻域高 **32.8 dB**、音高显著度逼近周期波——**那就是一个音**，听几十次必然腻。推倒重来才改成噪声承载。

**② "木质"靠宽共振峰给，不靠窄峰。**
频谱在 220 / 520 / 1100 / 2200 / 4200 Hz 有五个**宽达 0.7 个倍频程**的隆起。宽峰让人听出"一块木头"，窄峰才会让人听出"一个音符"。实测主谱峰只比邻域高 9.0 dB（对照：v1 窄峰版是 32.8 dB）。

**③ 瞬态在 1 ms 到峰。**
起振 0.54 ms、到峰 1.02 ms。快 attack 让它被大脑读作"**事件**"而不是"**乐音**"——事件不会疲劳，乐音会。同时快瞬态能穿透任何 BGM 与手机扬声器的窄带，永远清晰。

**④ 能量压在听不累的频段，且 90 ms 收干净。**
音色重心 1–2 kHz（听觉最灵敏但最不易疲劳的"话语频段"），4–16 kHz 比峰值低 **11.7 dB**（高频太多连续听会累），120–500 Hz 只低 4.1 dB（有重量，手机扬声器也发得出来）。全长 90 ms、无混响，最后 10% 已衰减到峰值下 **-51.7 dB**。连续触发不会糊成一片。

**⑤ 程序侧再加一层随机（重要）。**
`playbackRate` ±5% + `gain` ±5%。90 ms 的噪声型音效变调后听不出音高差，但能彻底打散"同一个采样播 50 次"的机械感。**这一步请务必实现**，它比换素材更有效。

### 5.2 `sfx_pick` vs `sfx_snap` —— 两个"木头声"必须能分辨

| | `sfx_pick`（拿起） | `sfx_snap`（放下） |
|---|---|---|
| 时长 | 80 ms | 90 ms |
| 起振 | 1.13 ms（软，3.5 ms 抬升） | 0.54 ms（硬，1.2 ms 抬升） |
| 音色重心 | **500–1000 Hz（闷）** | **1000–2000 Hz（亮）** |
| 高频 | 比峰值低 21.0 dB | 比峰值低 11.7 dB |
| 峰值 | -11 dBFS | **-8 dBFS**（更响） |
| 感觉 | "手指把板抬起来"——钝、闷、有余韵 | "板砸在桌上"——干脆、亮、短 |

两个声音刻意做成**同一材质、不同动作**：拿起是软的、闷的、不抢戏；放下是硬的、亮的、有奖励感。

### 5.3 `sfx_win` —— "轻轻点头"，不是胜利号角

`C5 → E5 → G5` 上行，间隔只有 120 ms（跳跃感来自**节奏的紧密**，不是音量）。最后一个 G5 延长并加一层两个八度的极弱泛音做木琴的"亮点"，1.0 s 短混响收尾。

- 没有镲片、没有低音倍频增强、没有长混响轰鸣、没有第二次上扬
- 只在最后 400 ms 淡出，给结算面板的淡入留位置
- 音高显著度 0.874 —— 这是**唯一允许有明确音高**的音效，它就是要被听成一个上扬的乐句

### 5.4 `sfx_tap` —— 本版做了（原可省略）

任务说 tap 额度紧张可以省略、让程序用 Web Audio 合成。因为本版音频是**程序化合成（0 积分）**，我做了一个真正的木质点击，比代码合成短噪声包络更贴合美术的"木头"材质：
50 ms / 峰值 -12 dBFS（四个音效里最轻）/ 音色重心 1–2 kHz / 4–16 kHz 已压掉 9.4 dB。
**程序不用再写 Web Audio 合成代码了**，直接播这个文件。

## 6. BGM 循环：循环点在第 70.000 秒，怎么保证无缝

### 6.1 三层保证

**① 振荡器频率量化到循环长度。**
所有正弦频率都被量化到 `k × 44100 / 3087000` 的栅格上（栅格间隔 0.0146 Hz，音乐上完全不可闻），保证每个正弦在这个长度内走**完整数个周期**——循环点不可能有相位跳变。

**② 混响用"循环卷积"做。**
不是把混响尾巴截断，而是让尾音**绕过循环点接回开头**（FFT 长度严格等于循环长度）。所以 70.000 s 处的混响是连续的，不是"断在一半"。

**③ 循环点落在真实乐句留白里。**
这是关键，因为 MP3 编码会在文件首尾插入静音（见 §6.2）。所以我把循环长度做成 **24 小节 + 2 拍留白 = 70.000 s**：
- 音乐在第 68.571 s（24 小节末）结束
- 68.571 → 70.000 s 是 1.43 s 的乐句留白：低频垫在这里平滑释放，只剩混响尾巴
- 循环点前 50 ms 实测 **-40.8 dBFS**，循环点后 50 ms 是 -16.6 dBFS（下一乐句的起音）

**④ 首尾强制归零。**
最后一步给首尾各 2 ms 加升余弦收敛到 0。这段区间本身已在 -40 dBFS 以下，2 ms 收敛完全不可闻，但让接缝在数学上**不可能**有咔哒声。

### 6.2 实测数据

| 指标 | 数值 | 判据 |
|---|---|---|
| 循环点样本跳变 | **0.0000013** | 全曲相邻样本差中位 0.0046 / 99.99 分位 0.0925 → 比正常波形变化小 5 个数量级 |
| 循环点前 50 ms | -40.8 dBFS | 在留白里 |
| 循环点后 50 ms | -16.6 dBFS | 下一乐句起音 |

### 6.3 MP3 编码填充：这是唯一需要程序注意的地方

MP3 编码器不写 gapless 元数据（`lameenc` 不支持），**解码后必然多出填充**。实测：

```
解码总长 3,088,512 采样
  = 前置填充  1,105 采样（25.057 ms）
  + 音乐本体 3,087,000 采样（70.000 s）
  + 尾部填充    407 采样（9.2 ms）
```

三种处理方式，任选其一：

| 方式 | 做法 | 结果 |
|---|---|---|
| **A（推荐）** Web Audio | `loopStart = 1105/44100 = 0.025057`，`loopEnd = (1105+3087000)/44100 = 70.025057` | **样本级精确无缝** |
| **B** Web Audio 偷懒 | `loop = true`，不设 loopStart/loopEnd（循环整个 3,088,512 采样缓冲） | 循环点有 34.3 ms 空隙，但**落在 -40.8 dBFS 的留白里，听不出来** |
| **C** `InnerAudioContext` | `innerAudioContext.loop = true` | 同 B，可用；但那套 API 对短音效延迟高，BGM 用它可以 |

> 结论：**A 最好，B/C 也听不出问题**——因为循环点是设计在留白里的。不必为这 34 ms 纠结。

## 7. 省略 / 降级 / 偏离说明

### 7.1 本版**没做**的（都属于下个版本范围）

| 没做 | 原因 |
|---|---|
| 七巧板（7 块）相关的任何音效 | v0.2 范围，本版不做 |
| UI 转场音（页面切换、面板滑入滑出） | v0.2；本版页面切换用静默 + 视觉动效，不硬凑 |
| 提示（每关 1 次）音效 | 策划清单里没有；v0.1 走静默。若验收后觉得需要，v0.2 补一个 `sfx_hint` |
| 重叠警告音（"有两块压在一起了"） | 策划清单里没有。**本版建议保持静默**——提示是文字淡出，加音效会变成"惩罚感"，与"不设失败"的基调冲突 |
| 星级逐颗点亮的音效 | 策划清单里没有；建议静默（`sfx_win` 的余韵正好覆盖这 360 ms） |
| 旋转 / 翻转音效 | 策划清单里没有。**建议 v0.1 保持静默**：旋转是 120 ms 的高频操作，加音效会吵；真要加，v0.2 用 `sfx_tap` 变调即可 |
| 结算/失败音乐、主界面独立音乐 | 本版只有一首 BGM。无失败设计（策划 §3.3 明确不设失败），所以不需要失败音乐 |

### 7.2 格式偏离：3 个短音效用 WAV 而不是 MP3

| | MP3 | WAV |
|---|---|---|
| 体积（90 ms） | 2.04 KB | **7.79 KB** |
| **编解码延迟** | **25.06 ms** | **0 ms** |
| 解码开销 | 每次播放要解一帧 | 直接读，零开销 |

实测 `lameenc` 编解码对任何长度都固定引入 **1105 采样（25.06 ms）** 延迟，与码率无关。对"拖起板"和"吸附咔"这种要求手感同步的音效，25 ms 是可感知的（叠加游戏自身音频延迟后可能到 40–60 ms）。WAV 8 KB 换掉这 25 ms，是本版最划算的一笔交易。

- 三个文件都远低于"单个音效 ≤40 KB"的上限（最大 7.79 KB）
- WAV 是标准 PCM，浏览器和微信小游戏都原生支持，无需任何解码库
- `sfx_win` 保留 MP3：1.2 s 转 WAV 会到 106 KB，超 40 KB 上限；而"成局乐句"晚 25 ms 完全无影响

#### 降级链（主理人 2026-11-18 要求，列入验收项）

WAV 万一在个别机型/加载路径上失败，不能变成静音。程序按下面的顺序加载，**同名不同扩展**，无需改引用名：

| 音效 | 首选 | 失败时回落 | 再失败 |
|---|---|---|---|
| `sfx_snap` | `assets/audio/sfx_snap.wav` | `assets/audio/mp3-fallback/sfx_snap.mp3` | 静默（不报错、不弹提示） |
| `sfx_pick` | `assets/audio/sfx_pick.wav` | `assets/audio/mp3-fallback/sfx_pick.mp3` | 静默 |
| `sfx_tap` | `assets/audio/sfx_tap.wav` | `assets/audio/mp3-fallback/sfx_tap.mp3` | 静默 |
| `sfx_win` | `assets/audio/sfx_win.mp3` | —（本身即 MP3，无回落） | 静默 |
| `bgm_main` | `assets/audio/bgm_main.mp3` | —（本身即 MP3） | 静默，但游戏照常可玩 |

```
audio-src/
├── bgm_main.mp3              683.93 KB
├── sfx_snap.wav                7.79 KB   ← 首选
├── sfx_pick.wav                6.93 KB   ← 首选
├── sfx_tap.wav                 4.35 KB   ← 首选
├── sfx_win.mp3                14.39 KB
└── mp3-fallback/                        ← 需要一起拷进 assets/audio/
    ├── sfx_snap.mp3             2.04 KB
    ├── sfx_pick.mp3             2.04 KB
    └── sfx_tap.mp3              1.22 KB
```

> ⚠️ `mp3-fallback/` **要整个目录拷到 `preview/assets/audio/mp3-fallback/`**，否则回落路径 404。多占 5.4 KB。
> 回落后音效会有 25.06 ms 延迟，请打一条 `console.warn` 记账（不要弹 UI），方便验收时发现是哪台机走了降级。

### 7.3 本版音频**不是** AI 生成

`audio-src/` 里没有用任何音乐生成服务，全部由 `gen_audio.py` 用 numpy 合成（733 行），所以：

- **积分消耗 0 分，10 分预算完整保留**
- 好处不只是省钱：AI 音乐生成**无法保证循环点无缝**（生成模型不做相位对齐）、**无法保证 90 ms 内收干净**、也无法控制"音高显著度"。这些硬指标本版全是算出来的，不是听天由命
- 代价：音色没有真录乐器的细腻度。对"休闲拼图 + 手机扬声器 + 全程 0.30 音量"这个场景完全够用

**建议（给主理人）**：既然音频这 10 分没用掉，可以考虑挪给美术（v0.1 美术只有 3 张图，30 分）或留给 v0.2 的七巧板音效。
